当前 NiaH parsing 全规则详解#

生成日期：2026-08-17 范围：当前本地实验链路中实际使用的 native-thinking trace parser、E1/E2/E3 重数 episode parser、最终 Total: 答案 parser，以及仅用于第 11 节对照实验的 restart-only E1 parser。

0. 先给结论：现在不是“一个 parser”，而是四个职责不同的解析层#

层 当前用途 是否使用 gold 主要输出
A. 最终答案 parser 判断原始输出或 cutoff 续写最终答了多少 是，只有在计算正确率时使用 gold N predicted_count、exact_count、格式合规性
B. 第一次 trace parser 找到第一个可可靠截断的城市列表，供 parse 分类、cutoff 和旧 geometry 使用 是 cut_char、城市序列、marker、trace 类别
C. 多轮 episode parser 在 thinking 中识别每一次完整计数 E1/E2/E3，供重数与逐轮 activation 分析使用 是 完成 episode、每项 rank/city/site、completion kind
D. restart-only E1 parser 检验默认 E1 完成条件是否造成选择偏差 是 仅改变第一条 raw sequence 是否注册为 E1

最重要的区分是：

parse hit ≠ trace one-to-one ≠ cutoff 完成 ≠ 最终答案正确
  • parse hit 只表示找到了受支持格式且有可靠终止证据的 trace。
  • one_to_one 才表示 trace 中的城市与 gold 一一对应；顺序可不同。
  • cutoff 完成 表示字符截断、token 对齐、闭合 thinking 和续写全部成功。
  • exact_count 只比较最终 Total: n 中的 n 是否等于 gold N。

此外，B 与 C 是两个刻意分开的 parser。B 回答“第一次可在哪里截断”；C 回答“哪些 rank 轨迹构成一次完成的计数”。不能用 B 的一次 parse hit 推断只有一个 episode，也不能用 C 的 episode 边界替代 B 的旧 cutoff 边界。

1. 公共输入、gold 与 reasoning-span 规则#

R1.1 输入文本字段#

独立 parser API 依次寻找：

  1. 顶层 raw_output_text；
  2. 若不存在，则使用 baseline.raw_output_text；
  3. 两者都没有时抛出错误，不生成伪造的 no-hit。

例：

{
  "baseline": {
    "raw_output_text": "<think>\n1. Chicago\n2. Baku\n</think>\nTotal: 2"
  },
  "gold_pairs": [{"city": "Chicago"}, {"city": "Baku"}],
  "model_label": "Qwen3-8B"
}

这个输入合法；parser 会从 baseline.raw_output_text 读取文本。

R1.2 gold 字段优先级和约束#

gold 依次从 gold_records、gold_pairs、relevant_records 中读取第一个非空 list。每项可以是城市字符串，也可以是含 city 的对象。

合法例子：

{"gold_records": ["Chicago", "Baku"]}
{"gold_pairs": [{"city": "Chicago", "score": 72}, {"city": "Baku", "score": 98}]}

非法例子：

{"gold_records": [{"city": "Chicago"}, {"city": "chicago"}]}

因为城市名按大小写不敏感方式必须唯一；空城市名和空 gold list 也会直接报错。

R1.3 模型族推断#

显式 model_family 只能是 qwen3 或 gemma4。没有显式值时，parser 在 model_label、model、model_id 中查找 qwen 或 gemma，否则报错。

例：model_label="google/gemma-3-4b-it" 会被推断为 gemma4；model_label="unknown-model" 不会被猜成某个模型族。

R1.4 reasoning span：Qwen#

Qwen 的 reasoning 起点是第一个 <think> 之后；若没有 opening tag，则从字符 0 开始。终点取最后一个 </think> 之前。

例：

<think>
1. Chicago
</think>
draft
</think>
Total: 1

Qwen trace parser 会使用最后一个 </think> 作为 reasoning 终点。这是为了适配 Qwen 输出中可能出现的重复 close；最终 Total: 不作为城市列表项。

R1.5 reasoning span：Gemma#

Gemma 的 opening delimiter 是：

<|channel>thought

close delimiter 是：

<channel|>

Gemma 使用 opening 后的第一个 close 作为 reasoning 终点。

例：

<|channel>thought
1. Chicago
<channel|>final
Total: 1

只有 1. Chicago 所在部分参与 trace parsing。

R1.6 close 缺失时的行为#

若没有 close tag，reasoning 延伸到整个 raw_output_text 末尾。parser 不会自动假定最后一个 item 已完成；是否 parse hit 仍取决于 item 边界和列表终止证据。

例：

<think>
1. Chicago

这一项虽有换行边界，但之后没有 close、非空 trailing prose、序号破坏或重启，因此没有列表终止证据，结果是 no-hit。

本节结论： parser 只看模型的 reasoning 区域；gold 和模型族是必需的实验元数据。delimiter 规则影响绝对字符坐标，因此下游 activation site 必须使用 parser 返回的绝对 span，不能自己再切一次字符串。

2. Gold city 匹配与逻辑 item 边界#

R2.1 城市名整词、大小写不敏感匹配#

城市名使用 (?<!\w)CITY(?!\w) 式边界，大小写不敏感。

  • chicago 可以匹配 gold Chicago。
  • gold Rome 不会匹配 chromed 中间的 rome。
  • 若 gold 同时可能出现长短重叠名，长名优先，避免把 Mexico City 截成较短城市名。

R2.2 显式列表按“不同 gold city”计数#

在显式列表中，同一 item 内同一个 gold city 重复两次，matcher 会先去重，所以仍算“恰好一个不同的 gold city”。

1. Chicago, yes Chicago
2. Baku
</think>

实际结果：接受城市序列是 Chicago, Baku，不是 Chicago, Chicago, Baku。

这与 fallback 不同：completion recap 和 audit fallback 保存每次城市 occurrence，所以 recap 中的 Chicago, Chicago, Baku 会保留重复。

R2.3 parser 不检查 score#

当前 trace parser 只使用 gold city 集合，不比较 item 中出现的数字与 gold score。

1. Chicago has score 999
2. Baku has score -7
</think>

若 gold city 是 Chicago/Baku，这两个 item 都可被接受；错误 score 不会使 parse 失败。score 正确性属于数据/答案评估，不属于 trace 边界定位。

R2.4 非 gold 城市对 matcher 不可见#

1. Chicago and London
2. Baku
</think>

若 London 不在该样本 gold 集合中，第一行仍被视为只含一个 gold city Chicago，因此可以接受。这是 gold-assisted parser 的明确限制：all_items_gold_city=True 的含义是“每个接受项都有且只有一个注册 gold city”，不是通用 NER 意义上的“行内没有其他城市”。

R2.5 物理换行是 item 边界#

1. Chicago
2. Baku

两个 item 的 item_boundary_kinds 都是 newline；item_end_char 不含换行，而 cut_char 保留最后一个接受项的换行。

R2.6 句号也可切出同一物理行中的多个逻辑 item#

只有当句号后是空白或文本结束，而且句号前已经是“受支持 marker + 恰好一个 gold city”，或句号后开始一个受支持 marker 时，才把它当逻辑边界。

First, I found Chicago. Then:Baku. Finally I found Taipei.

实际切成 3 个 item，边界都是 period，marker 规范化为 (1,2,3)。

R2.7 marker 自身的句点不能被误切#

1. Chicago
First. Baku

1. 和 First. 中的点是 marker 标点，不是句子边界。parser 会继续读 marker 后的城市内容；只有 item 末尾的句点或换行才是 item 边界。

R2.8 保守句末规则#

.、!、? 在 episode parser 中都能结束 sentence unit；第一次 trace parser 的行内 item 切分只使用句点 .。句点若紧接非空白字符，不切分。

First: Chicago.Then: Baku.

第一个句点后直接是 Then，因此不是合法保守边界；不能按这个位置拆成两个 trace item。

本节结论： 显式 trace 的基本单位不是“物理行”，而是保留精确字符 offset 的逻辑 item。城市匹配是 oracle-assisted、只关心 city、不关心 score；这保证 cutoff 边界稳定，但不能把 parser 命中解释为语义内容全部正确。

3. 显式 marker parser 的全部规则#

R3.1 candidate 必须从合法起点开始#

candidate 起始逻辑 item 必须同时满足：

  1. 含受支持 marker；
  2. 含恰好一个不同的 gold city；
  3. 有 newline 或 period 边界；
  4. 数字/序数 candidate 必须从 1/First 开始；bullet 可从任意受支持 bullet 开始。

反例：

2. Baku
3. Taipei
</think>

不能启动 indexed candidate，因为没有 1。

R3.2 阿拉伯数字 marker#

支持 数字. 和 数字)，marker 后空格可省略；序列必须从 1 开始严格递增。

1.Chicago
2)Baku
3. Taipei
</think>

实际结果：marker_kind=indexed，item_markers=(1,2,3)，one-to-one。

序列破坏会终止已有 candidate：

1. Chicago
3. Baku

实际结果：接受的 trace 只有 Chicago，termination_kind=marker_sequence_break，cut 在 1. Chicago\n 后。数字 candidate 没有“至少两项”的额外限制，因此强序列破坏可以终止单项 candidate。

序号重新从 1 开始也终止已有 candidate：

1. Chicago
2. Baku
1. Chicago

第一个 candidate 是 Chicago,Baku，termination_kind=marker_restart；第三行不包含在第一次 cutoff prefix 中。

R3.3 英文序数 marker#

支持 First 到 Twentieth，也支持 Firstly 到 Twentiethly；大小写不敏感。允许单/双星号或反引号 Markdown 包裹，允许 . ) : , - 或空格分隔，marker 后空格可省略。

**First:**Chicago
`Second`)Baku
Thirdly-Taipei
</think>

规范化 marker 为 (1,2,3)。

英文序数也必须从 First 开始并严格递增。gold N>1 时，孤立的一个 First 项即使遇到 close 也被拒绝：

First: Chicago
</think>

实际结果：detected=false，拒绝原因是 ordinal sequence 至少需要 2 项。这项限制用于避免把普通 prose 中的 “First” 误当完整目标列表。若 gold N=1，则单项 First 可以接受。

R3.4 Then 和 Finally#

它们只能加入已经由 First 启动的 ordinal candidate，不能自己启动 candidate。

  • Then 固定规范化为 rank 2，所以只在当前 expected=2 时接受。
  • Finally 规范化为当前 expected rank，并设置 finally_seen=True。
  • Finally 本身就是终止证据；后续同 family marker 不再接入这个 candidate。
First, I found Chicago. Then:Baku. Finally I found Taipei.

实际结果：markers 为 (1,2,3)，城市为 Chicago,Baku,Taipei。

反例：

Then: Chicago
Finally: Baku
</think>

没有 First，不能建立 ordinal candidate。

若正在扫描 indexed 或 bullet candidate，Then: Baku 不被当作 marker-family change，而只作为 bridge prose；transition 词的顺序意义只在 ordinal 上下文中生效。

R3.5 bullet marker#

支持 -、单个 *、•，bullet 与正文之间空格可省略，同一个 candidate 内三种符号可以混用。

-Chicago
*Baku
•Taipei
</think>

实际结果：marker_kind=bullet，表面 markers 保存为 ('-', '*', '•')，one-to-one。

以下不接受为 bullet：

**Chicago**
-> Baku

双星号是 Markdown 强调；-> 是推导箭头，均不是 bullet item。

R3.6 每个显式 item 必须恰好含一个不同的 gold city#

合法：

1. Chicago has score 72

非法：

1. Chicago and Baku

后者同一 item 含两个不同 gold city，不能接受为一个计数项。

若 expected marker 不含恰好一个 gold city：

  • 已接受至少 2 项，或 gold N=1：它可作为终止证据，termination_kind=expected_marker_not_gold_city；
  • gold N>1 且此前只有 1 项：整个 candidate 不成立。

对照例子：

1. Chicago
2. London
</think>

若 London 非 gold，实际 no-hit。

1. Chicago
2. Baku
3. London
</think>

实际接受 Chicago,Baku，第三行证明列表结束。

R3.7 bullet 的单项防误判规则#

gold N>1 时，一个 gold bullet 后紧接 non-gold bullet，不足以证明前者是目标城市列表：

- Chicago
- Total records: 1
</think>

结果 no-hit，拒绝原因 single_city_item_before_non_gold_bullet。

有两个已接受 bullet 后，non-gold bullet 可以终止：

- Chicago
* Baku
• Total records: 2

接受 Chicago,Baku，termination_kind=next_non_gold_bullet，cut 在 * Baku\n 后。

R3.8 bridge line 可以跨段拼接#

空行、普通解释、小标题、以及不构成“同 family marker + 单一 gold city”的文本可出现在两个已接受 item 之间。

1. Chicago

Checking again.
2. Baku
3. Taipei
</think>

实际仍是一个 indexed candidate，bridge_line_count=2（空行和解释行各 1）。bridge 只连接前后合法 item，不会自己成为 item。

R3.9 marker family 改变#

扫描中若遇到“另一种非 transition marker + gold city”，当前 candidate 立即终止：

1. Chicago
2. Baku
- Taipei

indexed candidate 只接受前两项，termination_kind=gold_city_marker_change。后面的 bullet 不进入第一次 candidate。

R3.10 合法终止证据全集#

显式 candidate 必须具有以下至少一种终止证据：

termination_kind 规则 具体例子中的终止行
thinking_close 已有 item，reasoning 随后遇到官方 close 2. Baku\n</think>
trailing_prose 最后一项后直到 reasoning 末尾存在非空 prose Therefore the total is two.
marker_restart 同 family 序号重新从 1/First 开始 1. Chicago 出现在已有 1,2 后
marker_sequence_break 同 family 序号不等于 expected 1 后直接出现 3. Baku
expected_marker_not_gold_city 合法 expected marker 但不含恰好一个 gold city，且已有足够项 1,2 后出现 3. Total
next_non_gold_bullet 至少两个 bullet item 后出现 non-gold bullet - Total records: 2
gold_city_marker_change 另一个 marker family 开始含 gold city 的项 数字列表后出现 - Taipei
final_transition 已接受 Finally，即使无 close 也可终止 Finally: Taipei.

用来证明终止的后续行不进入 cutoff prefix。例如：

1. Chicago
2. Baku
Therefore there are two records.

cut 严格位于 2. Baku\n 后，不保留 Therefore...。

只有末尾空白、没有 close 的情况不算 trailing_prose，所以不能单独证明列表完成。

R3.11 返回第一个可靠终止的显式 candidate#

parser 从前到后扫描，一旦遇到第一个 terminated=True 的显式 candidate 就立即返回，不按 coverage 最大化挑选后面的列表。

1. Chicago
2. Baku
Done with this list.
1. Chicago
2. Baku
3. Taipei
Done again.

实际返回第一段 Chicago,Baku；虽然第二段覆盖更多，也不会事后替换第一段。这正是“第一次 trace cutoff”的定义。

R3.12 parse hit 不要求覆盖全部 gold，也允许跨 item 重复#

gold 为 Chicago,Baku,Taipei 时：

1. Chicago
2. Taipei
</think>

是 parse hit，类别 partial_unique。

1. Chicago
2. Chicago
3. Baku
</think>

也是 parse hit，类别 partial_with_duplicates，duplicate_gold_city_items=1。

本节结论： 显式 parser 的核心不是“找全 gold”，而是“从一个可靠起点建立格式一致的 city-item 序列，并找到可信终止边界”。因此 partial 和 duplicate trace 都能命中；正确性必须看后续分类字段。

4. 没有显式 marker 时的两个 fallback#

两个 fallback 只有在没有任何显式 candidate 成功终止时才运行；优先顺序是 completion recap，再是 V4.4 audit sentence chain。

R4.1 completion recap 必须位于 reasoning 后段#

候选句的结束位置必须满足：

sentence_end >= 0.45 × reasoning_character_length

也就是句子至少结束在 reasoning 的最后 55% 内。长句可以从阈值前开始，只要结束位置跨入后段。

例：前面有较长扫描过程，末尾出现：

Let me count again. Chicago, Chicago, Baku.

后一句可成为 recap；城市序列原样保存为 Chicago,Chicago,Baku。

R4.2 recap 必须有窄集合 counting cue，或下一句一致的 count summary#

cue 可在城市句自身，也可在紧邻前一句。支持的语义包括 counting them again、let me count、recounting、tallying up、cities listed/found/identified/counted、in total、there are exactly N cities 等。

Let me count again. Chicago, Baku, Taipei.

合法：前一句提供 cue。

城市句和前一句都无 cue 时，紧邻下一句可以闭合，但 summary 数必须等于该城市句实际 mention 数；数字或英文基数词 1–20 都可。

Chicago, Baku, Taipei. That's three cities.

合法。

Chicago, Baku, Taipei. That's two cities.

不合法，因为 summary 说 2，而实际列了 3 个 mention。

R4.3 recap 必须紧凑#

从首个到末个 gold-city mention 的跨度不能超过：

max(220, 55 × mention_count) characters

这防止把散布在整段扫描 prose 中的城市误拼成 recap。

I saw Chicago and later checked Baku.

即使紧凑，只要没有 counting cue，也仍是 no-hit。

当前 recap cue 的词表是封闭的，完整分组如下：

  1. counting [them] [again]；
  2. let me、let's、I'll、we'll + count/recount [them] [again]；
  3. tally/tallying [up]，以及 recount/recounting/recounted；
  4. cities/entries/records/instances/mentions + listed/found/identified/counted/are；
  5. 上述名词 + mentioned/seen are/were；
  6. 上述名词 + I/we found/identified/counted/listed [are]；
  7. found/identified/listed the following/these；
  8. all [the] cities/entries/records/instances/mentions 或 the ... listed；
  9. in total、total of；
  10. 可选 there are/were exactly + 数字或 one–ten + 可选 explicit、可选 city-score audit + 上述名词；
  11. only/single [city-score audit] record is。

不在这些组里的近义表达不会仅凭语义相似自动命中。例如 I reviewed Chicago and Baku 不在 cue 集合中。

R4.4 单城市 recap 的额外限制#

通常 recap 至少需要两个 gold-city mention。只有 gold N=1，并且同一句明确含 one、1、only 或 single，单城市 recap 才接受。

The only city-score audit record is Zagreb's 64.

当 gold 只有 Zagreb 时可接受；同一句若没有 one/only/single 信号则拒绝。

R4.5 recap 不要求完整覆盖，保留重复#

Counting them again: Chicago, Chicago, Baku.

gold 为 Chicago/Baku/Taipei 时，仍是 parse hit；分类为 partial_with_duplicates。fallback 给这些 occurrence 合成 item_markers=(1,2,3)，但这些是顺序代理，不是真实 index token。

R4.6 recap cutoff 边界#

cut_char 放在 recap 句的终止标点之后；每个城市 mention 的精确 span 分别保存。若下一句只是 count summary，它用于证明 recap，却不进入保留 prefix。

Chicago, Baku, Taipei. That's three cities.

cut 在 Taipei. 后，不保留 That's three cities.。

R4.7 V4.4 audit sentence chain 的严格模板#

若 recap 也没有命中，parser 查找 reasoning 中所有严格匹配下式的句子：

In the 2024 city score audit, <GOLD_CITY> received a score of <INTEGER>.

城市和整数可以被单/双星号或反引号包裹。

In the 2024 city score audit, **Chicago** received a score of **72**.
In the 2024 city score audit, `Baku` received a score of `98`.

合法，保存城市序列 Chicago,Baku。

R4.8 audit fallback 只验证模板与 gold city，不验证 score#

In the 2024 city score audit, Chicago received a score of 999.

只要 Chicago 是 gold city，仍匹配；999 不需要等于 gold score 72。

普通 prose 不匹配：

I found Chicago with score 72.

因为缺少完整固定模板。

R4.9 audit chain 使用所有匹配 occurrence#

所有模板 match 按文本顺序组成一个隐式序列；可遗漏、可重复，cut 在最后一个匹配句的句点之后。它没有真实 index token，后续 geometry 中的 marker site 只能解释为模板前缀/隐式顺序代理，不能与数字标号混称。

本节结论： fallback 是为了覆盖 Qwen 常见的无显式 marker 计数，但仍保持高精度。它们不是任意城市 NER：recap 需要后段、计数 cue 和紧凑性；audit 需要精确 V4.4 模板。

5. Trace 分类、no-hit 诊断、坐标与 -v#

设接受城市序列为 O，gold 城市序列为 G；比较时大小写不敏感。

R5.1 one_to_one#

形式化条件：

len(O) = len(G)  且  Counter(O) = Counter(G)

即每个 gold city 恰好一次，无遗漏、无重复。顺序不作为正确性的必要条件。

  • forward：O == G。例：gold Chicago,Baku,Taipei，trace 同序。
  • reverse：O == reversed(G)。例：Taipei,Baku,Chicago。
  • other_permutation：其余排列。例：Baku,Chicago,Taipei。

三者都属于 trace_one_to_one=true。

R5.2 full_coverage_with_duplicates#

每个 gold city 至少出现一次，但 trace 中存在重复。

Chicago, Baku, Taipei, Baku

coverage 完整，Baku 重复一次。

R5.3 partial_unique#

至少遗漏一个 gold city，接受项没有重复。

Chicago, Taipei

gold 为 Chicago/Baku/Taipei 时遗漏 Baku。

R5.4 partial_with_duplicates#

既遗漏 gold city，又有重复。

Chicago, Chicago, Baku

遗漏 Taipei，Chicago 重复。

R5.5 no_parser_hit#

没有任何候选同时满足受支持格式与可靠终止边界。no-hit 仍会返回“最佳失败 candidate”的诊断字段；最佳值按以下字典序选择：

  1. coverage_count 最大；
  2. 再取 item_count 最大；
  3. 再取出现更早者。

例：前面失败候选覆盖 Chicago，后面失败候选覆盖 Chicago/Baku，则 no-hit 记录后者的 marker 与 coverage，但 detected 仍为 false、cut_char 仍为 null。诊断字段不能当作 parse hit 使用。

R5.6 matched_gold_cities 去重，item_gold_cities 不去重#

1. Chicago
2. Chicago
3. Baku
  • item_gold_cities = (Chicago, Chicago, Baku)；
  • matched_gold_cities = (Chicago, Baku)；
  • coverage_count = 2；
  • duplicate_gold_city_items = 1。

R5.7 字符坐标语义#

  • reasoning_start_char/end_char：reasoning 在完整 raw output 中的绝对范围；
  • list_start_char：candidate 第一项起点；
  • item_start_chars：每个逻辑 item 的绝对起点；
  • item_end_chars：每项正文终点，不含换行/句号边界；
  • item_boundary_kinds：newline、period、recap_period 或 audit_sentence_period；
  • cut_char：最后一项结束边界之后的绝对字符位置。

例如：

<think>
1. Chicago
2. Baku
Therefore...

cut_char 指向 2. Baku\n 后；因此 raw_text[:cut_char] 保留该换行，但不含 Therefore...。

R5.8 cut_char 不等于 total-count commit#

若模型写：

3. Taipei
Count: 3

第一次 trace parser 的 cut 在 3. Taipei item 边界后，通常不保留 Count: 3。所以“城市已经写完”不自动等于“模型已经在后续 marker/summary 中提交 total count”。这是解释 cutoff 行为与 activation 不一致时必须保留的限制。

R5.9 -v 汇报规则#

-v 不是逐行 debug。全部 JSONL parse 完成后才输出/保存：

  • 总行数、parser hit 数与比例；
  • one-to-one 数与全体比例；
  • coverage complete 数与全体比例；
  • trace_category、marker_kind、termination_kind、trace_order_class、gold N 分类；
  • model × trace category 交叉分类。

例：两条输入中一条 one-to-one、一条 no-hit，则 parser_hit_rate=1/2、trace_one_to_one_rate_all=1/2。这里分母是全部输入，不是仅 hit 子集。

独立 parser 的 -v 不计算最终答案准确率，因为它没有把 answer evaluation 当作 trace 分类的一部分；需要下游显式 join evaluation.exact_count。

本节结论： trace 分类是对已接受城市序列的 multiset 审计。item_* 保存逐次访问，matched_* 保存 distinct coverage；二者不可互换。字符坐标描述文本边界，不直接声明内部计数状态已经完成。

6. 从 parse hit 到 cutoff 的下游规则#

R6.1 哪些 trace 类别可以尝试 cutoff#

当前行为实验允许所有 parse hit 进入 cutoff 尝试：one-to-one、full coverage with duplicates、partial unique、partial with duplicates 都可以。trace 类别只用于分层分析，不是 intervention eligibility gate。

R6.2 字符 prefix 必须精确 round-trip#

目标 prefix 是：

raw_text[:cut_char]

tokenizer 重新编码后再解码必须逐字符等于该 prefix；否则 text_prefix_did_not_round_trip，不执行干预。

R6.3 token 边界跨界时只重 tokenize 后缀#

若 newline cut 落在一个编码了双换行的 token 内，不能用原始 token ID 的简单前缀表达。当前规则允许从第一个不同 token 开始重 tokenize，但：

  1. 更早的 baseline token prefix 必须完全相同；
  2. 新 token 序列解码必须精确等于字符 prefix；
  3. 这不是“取最近 token”的近似。

结果记录 literal_baseline_token_prefix 或 text_exact_boundary_retokenization。

R6.4 闭合 thinking 并续写#

精确 prefix 后追加模型官方 close delimiter，再沿用注册的 seed、temperature、top-p、top-k 继续生成；保留 prefix、close 与 continuation 总长度不能超过原 4096-token 输出预算。

例：Qwen 使用 </think>；Gemma 使用 <channel|>。

R6.5 all-sample policy 回退#

没有 parse hit、token 对齐失败、无剩余预算或生成失败时，policy 输出回退到原始 baseline。于是：

policy accuracy = 所有样本按“成功 cutoff 用 cutoff，否则用 baseline”后的准确率

它不同于 completed-only cutoff accuracy，后者的分母只包含实际完成 cutoff 的样本。

本节结论： parser 只给候选字符边界；真正完成 cutoff 还需通过严格 token 对齐和生成流程。parser hit rate、completed rate、completed-only accuracy 和 policy accuracy 是四个不同指标。

7. 多轮重数 E1/E2/E3 episode parser 的全部规则#

这一 parser 位于当前 exact-K/episode clarity 分析代码中，目标是识别“完成的运行计数轨迹”，不是替代第一个 trace parser。

R7.1 sentence unit 切分#

reasoning 先按物理换行切分，再在 . ! ? 处分 sentence unit；标点后必须是空白或文本末尾，紧随的引号、右括号、Markdown 结束符会一起包含在 unit 末尾。

Chicago is relevant. First.

会形成城市 unit Chicago is relevant. 和 rank-only unit First.。

R7.2 rank 证据：行首数字#

支持 1–2 位数字，后接 . 或 )，位于 unit 开头，可有有限的 Markdown/引用前缀。

1. Chicago

由于句点也会切 unit，实际常形成 rank-only 1. 与 city unit Chicago，随后通过邻接规则关联，evidence_kind=rank_before_city。

R7.3 rank 证据：行首英文序数#

episode parser 支持 First–Twentieth，但不使用 Firstly 等 -ly 形式。

Third: Taipei

得到 rank 3、evidence_kind=ordinal_prefix。

R7.4 rank 证据：labeled numeric rank#

支持关键词 count、record、entry、excerpt、instance、item、found，后接可选 number/no.、分隔符及 1–2 位数字。

Chicago was found count=1.
Baku was found item #2.

分别得到 rank 1、2，evidence_kind=labeled_rank。

R7.5 rank 证据：trailing ordinal#

支持如下语义尾标：

Chicago ..., that is first.
Baku ..., that's the second record.
Taipei ..., this is the third city.

分别得到 rank 1、2、3，evidence_kind=trailing_ordinal。

特别注意：

Beijing ..., that is one.

不匹配 trailing ordinal，因为 one 不是 first。只有精确的：

Beijing ..., that is one record.

才由专门的 cardinal-one 规则得到 rank 1，evidence_kind=cardinal_one。

R7.6 城市与 rank 可在同一 unit，也可在相邻 rank-only unit#

同一 unit 例子：

Chicago is relevant, that is first.

得到 (city=Chicago, rank=1, trailing_ordinal)。

rank 在城市后：

Chicago is relevant. First.

只要相邻 gap ≤100 字符、rank unit 不含 gold city且只有一个 rank，得到 rank_after_city。

rank 在城市前：

1. Chicago

得到 rank_before_city。

若前后两侧都存在合格 rank-only unit，选择字符 gap 更小者。

R7.7 单个 event 的唯一性条件#

城市 unit 必须恰好有一个 gold-city occurrence；不是“一个不同城市”。因此：

Chicago, yes Chicago, count=1.

含两个 occurrence，会被 episode parser 拒绝为直接 event；这与第一次 trace parser 的显式 item 去重规则不同。

rank 方面，同一 unit 的等价重复信号会按 rank 去重：

1. Chicago, count=1.

两个证据都指向 rank 1，最终只保留一个 event。这个具体写法会先在 1. 后切 sentence unit，城市 unit 内的直接证据是 count=1，所以核验结果为 labeled_rank: count=1。若改成不触发句点切分的：

1) Chicago, count=1.

则 prefix 与 labeled evidence 位于同一 unit；二者 rank 相同而被去重，按检测顺序保留 indexed_prefix。因此“等价证据合并”是稳定规则，最终保存哪个 evidence_kind 还取决于 unit 切分与证据检测顺序。

冲突 rank 会拒绝整个 unit：

1. Chicago, count=2.

同时出现 rank 1 和 2，因而没有 event。可执行核验中，这会导致整段不能建立从 1 开始的完成 sequence。

R7.8 event rank 范围#

只接受 1–20。0、21 或更大的 rank 不成为 RunningCountEvent。这解释了 episode parser 的理论上限为何可能高于数据 v4.4 的 gold N≤10：parser 的防御性语法上限是 20，但正式 v4.4 gold count 仍最多 10；二者不是数据设置变化。

R7.9 event 的四个关键位置#

每个 event 保存：

  • city_end_char：城市名最后一个字符之后；
  • city_unit_end_char：包含城市的 sentence unit 末尾；
  • rank_evidence_end_char：rank 文本及相邻终止标点之后；
  • semantic_end_char = max(city_unit_end_char, rank_evidence_end_char)。

例如：

Chicago is relevant, that is first.

city_end 在 Chicago 后，rank_evidence_end 在 first. 后，semantic_end 在整个句子末尾。

Chicago is relevant. First.

city_end 在 Chicago 后，city_unit_end 在第一个句点后，rank_evidence_end/semantic_end 在 First. 后。因此 cutoff/activation 若声称“这次 item 的 rank 已知”，应使用 semantic_end，不能只用 city end。

R7.10 sequence 必须从 rank 1 开始#

events 按 semantic/trace end 排序。只有 rank 1 能启动 sequence；之后只接受严格 +1。

2. Baku
3. Taipei

不会建立 sequence。

1. Chicago
3. Taipei
2. Baku
3. Taipei

rank 3 在 expected=2 时被忽略，但不会破坏当前 sequence；随后 rank 2、3 仍可接入。这是“跳号 event 被忽略直到合法延续或 rank-1 重启”，不是第一次 trace parser 的“跳号立即终止”。

R7.11 相同 rank + 相同 city 的重复 event 会替换前者#

若当前末项和新 event 的 rank、city 都相同，保留后出现的 event，通常代表更显式的 Count=k commit。

Chicago ... that is first. Chicago ... count=1.

若两者被识别为连续同 rank/city event，sequence 中只保留后者的位置。

相同 rank 但不同 city 会被当作新的 rank-1 restart（仅 rank=1 时）或被忽略（rank>1），不会按“重复等价证据”合并。

R7.12 rank 1 重启开启新 raw sequence#

当前 sequence 已存在时，新的 rank 1 会保存旧 sequence，并启动新 sequence。

1. Chicago
2. Baku
3. Taipei
Wait, count again.
1. Chicago
2. Baku
3. Taipei

产生两条 raw sequence；若两条都通过完成条件，则是 E1、E2，structural_recount=true。

R7.13 完成条件一：terminal rank 到达 gold N#

若 sequence 末 rank 等于 gold city 数 N，并且长度至少为 1（N=1）或 2（N>1），则完成。

  • 后面没有下一条 sequence：completion_kind=reached_gold_count；
  • 后面还有 rank-1 restart：rank_restart_reached_gold。
1. Chicago
2. Baku
3. Taipei
</think>

gold N=3 时是 reached_gold_count。

注意：完成只看 terminal rank，不要求城市 multiset one-to-one。1.Chicago / 2.Chicago / 3.Baku 也可能成为完成 episode，但分类会是非 one-to-one。

R7.14 完成条件二：matching closure summary#

若 terminal rank 没到 gold N，但从最后城市 unit 结束到下一次 restart/ reasoning 末尾之间的 summary 写出的 count 与 terminal rank 一致，则完成。

支持的结构包括：

  • final count/tally ... N；
  • total、total count、total of ... N；
  • that's/that is ... N；
  • there are/were N；
  • I found/identified/counted/listed N；
  • N entries/records/instances/cities。

数字与英文 one–twenty 均可。

1. Chicago
2. Baku
That is a total of 2.

gold N=3 时仍注册一个 closure_summary episode，terminal running index 为 2，trace 为 partial。

若后面还有 restart，则 kind 为 rank_restart_with_matching_summary。

R7.15 完成条件三：最后 raw sequence 与最终 Total: 一致#

仅对最后一条 raw sequence：若 raw output 中最后一个 Total: d 的 1–2 位非负整数等于 terminal rank，也可注册 final_answer_agrees。

<think>
1. Chicago
2. Baku
I will stop.
</think>
Total: 2

gold N=3 时，若没有 matching closure，这条最后 sequence 仍可因 final answer agrees 完成。

这里的 _FINAL_TOTAL_RE 只是 episode completion 证据，语法比正式最终答案 evaluator 更窄：只接受 1–2 位非负整数。不要把它当作最终准确率 parser。

R7.16 minimum length#

gold N>1 时，任何默认完成路径都要求 sequence 至少 2 个 event；gold N=1 时只需 1 个。

1. Chicago
Total: 1

gold N=3 时单项不因 final answer agrees 注册；它计入 incomplete_sequences。

R7.17 incomplete sequence 与 episode 编号#

不满足任一完成条件的 raw sequence 不进入 episodes，只使 incomplete_sequences += 1。E1/E2/E3 是“完成 episode 的顺序编号”，不是所有 raw sequence 的编号。

因此一条开头 incomplete sequence 被丢弃后，下一条完成 sequence 会被命名为 E1。这正是后来 restart-only 对照要审计的选择偏差。

R7.18 recount/reflection cue 只做诊断，不决定结构#

strong_recount_cue 检查诸如 count again、recount、start over、count from the beginning、one more time、second pass。

reflection_cue 检查 wait、actually、double-check、verify again、make sure、did I miss 等。

完整 strong recount 形式为：recount/count/list [them] again、start/starting [the count] over、count/counting from [the] start/beginning、one more count/time、second count/pass。完整 reflection 形式为：wait、actually、double-check/double check、check again、verify again、make sure、might have missed、did I miss。

Wait, let me count again.

会同时设置 strong recount 与 reflection，但只有实际检测到至少两个完成 episode 时，structural_recount 才为 true。反过来，即使没有这些文字 cue，只要出现两条完成的 rank-1 sequence，仍是 structural recount。

R7.19 episode 内 trace 分类#

与第一次 trace parser相同，episode 的城市序列按 one-to-one、forward/reverse/other permutation、coverage 和 duplicate 分类；这些不是 episode completion gate。

例：gold Chicago,Baku,Taipei：

1. Baku
2. Chicago
3. Taipei

完成且 one-to-one，order_class=other_permutation。

R7.20 exact-K 样本定义#

exact-3 指 episode_count == 3，即恰好三次“通过完成条件的 episode”。它不等于文本中出现三次 1.，也不等于 recount cue 出现三次。

本节结论： episode parser 是“gold-city observation + rank evidence + 顺序轨迹 + 完成证据”的四层组合。E1/E2/E3 边界采用 semantic_end，保证城市和 rank 证据都已经出现；但默认会丢弃 incomplete raw sequence，因此 episode 编号存在条件选择，需要下一节的对照规则审计。

8. restart-only E1 对照 parser#

R8.1 只放宽第一条 raw sequence#

对照 parser 的唯一改动是：若第一条 raw sequence 后面存在另一条由 gold-city rank-1 event 开始的 sequence，则第一条无条件注册为 E1。

它不要求第一条：

  • 到达 gold N；
  • 有 matching closure；
  • 与最终 Total: 一致；
  • 长度至少 2。

E2/E3 及后续 sequence 仍使用 R7.13–R7.16 的默认完成条件。

R8.2 具体对照例子#

gold 为 Chicago/Baku/Taipei：

1. Chicago
Start the count over.
1. Baku
2. Chicago
3. Taipei
Count again.
1. Chicago
2. Baku
3. Taipei

默认 episode parser：

  • 第一条 singleton sequence incomplete；
  • 后两条完成；
  • episode_count=2，incomplete_sequences=1。

restart-only 对照：

  • 第一条注册为 E1，kind=e1_followed_by_gold_city_rank1；
  • 后两条仍按默认规则注册为 E2/E3；
  • episode_count=3，incomplete_sequences=0。

R8.3 一个细微边界：相同 city/rank 的紧邻重复可能先被去重#

sequence assembly 在 completion classifier 之前运行。若第一条末项和后来的 event 都是完全相同的 (rank=1, city=Chicago)，后者可能按“相同 rank + 相同 city 的更晚证据”替换前者，而不是建立 restart。只有 _deduplicate_and_sequence 已经检测到下一条独立 rank-1 sequence时，restart-only 规则才会生效。

例：

1. Chicago
1. Chicago
2. Baku
3. Taipei

前两个完全相同的 rank-1/city 可能合并为一个 sequence 起点；不能仅凭文本有两个 1. 就断言存在 E1 restart。

R8.4 该规则不是当前主 parser#

restart-only 只用于报告中的 counterfactual 章节，回答“如果 E1 只由后续 rank-1 重启来界定，exact-3 cohort 和逐轮结论怎样变化”。正式主结果若未明确标注 restart-only，仍使用第 7 节默认 completion rules。

本节结论： restart-only 不是扩大通用 parse hit 的新默认，而是有针对性的 E1 选择偏差敏感性分析。解读图表时必须同时看 parser schema/章节标签。

9. 最终 Total: 答案 parser#

R9.1 先分离 reasoning 与 final#

Qwen 使用最后一个 </think> 后的文本作为 final；Gemma 使用第一个 <channel|> 后的文本。若 inference backend 已经移除 reasoning channel 且没有任何 thinking delimiter，则整个输出按 final 处理。

R9.2 Total: 必须独占一行，但可有额外 final prose#

正式 parse_total 在 final 中寻找大小写不敏感的完整行：

Total: <signed integer>

允许行首/行尾空白和若干已注册 end token；若有多个匹配行，取最后一个。

Total: 2
Correction.
Total: 3

实际 predicted_count=3。

final 最外层若完整包在 <response>...</response> 或 [RESPONSE]...[/RESPONSE] 中，会先去掉 wrapper 再解析。例如：

<response>
Total: 3
</response>

等价于 Total: 3。

The answer is 3.

没有 Total: 完整行，predicted_count=null、parse_status=parse_fail。

R9.3 数值可为负数#

Total: -1

可以解析为 -1，但对 N≥1 的计数任务当然不正确。

R9.4 exact_count#

exact_count = (predicted_count == len(gold_pairs))

若 parse 失败，predicted_count=None，所以 exact_count=false。这项准确率不要求 final 只有一行。

R9.5 格式合规与 exact count 分开#

native thinking 的 prompt 要求 final 恰好一行 Total: n。因此：

The answer follows.
Total: 3

可解析、exact_count=true，但 response_format_compliant=false。

registered_success = exact_count
                     AND response_format_compliant
                     AND finish_reason != "length"

当前很多 cutoff/accuracy 图使用的是 evaluation.exact_count，不是更严格的 registered_success；报告中若写“正确率”，必须指明是哪一个字段。

允许出现在 Total: 行尾、仍被当作格式字符的可选 end token 是：<|im_end|>、<turn|>、<|endoftext|>、<｜end▁of▁sentence｜>。其他任意文字不能放在同一 Total: 行上。例如 Total: 3 because... 不匹配。

R9.6 enumeration prompt 的最终答案规则#

对于 roadmap 的 indexed/bullet enumeration prompt，final 还会解析：

1. Chicago: 72
2. Baku: 98
Total: 2

或：

- Chicago: 72
- Baku: 98
Total: 2

indexed 必须从 1 连续递增；混合 marker、使用错误 marker、没有 records 都会使 enumeration format 不合规。这里会比较 city-score pairs；它是最终回答格式审计，不是 native-thinking trace parser。

具体边界：indexed final 只接受 1. City: score，不接受 1) City: score；bullet final 只接受 - City: score，不接受 * City: score。score 允许负整数。Total: 必须是最后一个非空行，且此前每个非空行都必须完全匹配所选 prompt mode 的 record 格式。

R9.7 evaluator 中较粗的 repetition audit#

最终 evaluator 还保存一组旧式/粗粒度 overthinking 诊断：

  • 非空 reasoning 行先小写并压缩空白，完全相同的额外出现计为 reasoning_duplicate_lines；例：Check Chicago 写两行，第二行计 1 次重复。
  • 行首 1./1) 式数字序列中，只要当前 index <= 上一个 index，就使 reasoning_enumeration_restart_count += 1；例：1,2,3,1 计 1 次 restart，1,2,2 也计 1 次。
  • reasoning 中精确形如 1. City: score 或 - City: score 的 record pair 重复，计入 reasoning_duplicate_record_mentions。
  • finish_reason="length"、序号重启、record 重复、整行重复分别加入 overthinking_signals。

这套 audit 不等于第 7 节 episode parser：它不要求 gold city、rank evidence 与完成条件，只是粗粒度字符串统计。当前正式“发生几次重数”的分析应以完成 episode 数为主，这些字段只能作为补充诊断。

本节结论： 最终答案 parser 与 trace/episode parser 完全分离。一次 trace 可以 one-to-one 但最终 Total: 错；也可以 trace partial 而最终 Total: 正确。分析 activation 与行为一致性时必须明确 target 是 gold N、episode terminal rank，还是模型最终 predicted count。

11. 最终总括#

目前第一次 trace parser 的正式定义是：在对应模型的 reasoning span 中，优先寻找第一个“受支持 marker、每项一个注册 gold city、具有可靠 item 与终止边界”的显式序列；若没有，再尝试保守的后段 recap 和严格 V4.4 audit 模板。它允许遗漏和跨 item 重复，随后用互斥 trace category 分类。

目前 E1/E2/E3 parser 的正式定义是：把单一 gold-city observation 与唯一 rank 证据配对，按 1,2,3…建立 raw sequence，并通过到达 gold N、matching closure 或最后 Total: 一致来判断完成 episode；只对完成 episode编号。restart-only 版本仅用于测试被默认规则丢弃的第一条 incomplete sequence是否改变 exact-3 结论。

因此，任何后续报告至少应同时标明：使用 B 还是 C、marker/evidence kind、boundary/site、trace category、completion kind、最终正确性字段，以及是否启用了 restart-only counterfactual。缺少其中任何一项，都可能把“文本边界识别”“trace 正确”“内部 activation 可分”和“最终行为正确”混为一谈。
